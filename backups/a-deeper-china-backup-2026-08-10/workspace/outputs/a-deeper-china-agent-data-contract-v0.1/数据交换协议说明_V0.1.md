# A Deeper China｜智能体—数据库—人工审核数据交换协议 V0.1

## 为什么先做协议

网站只是入口；真正的产品是从客户语言中提取旅行决策，再将**可审计的城市内容**和**人工复核结果**组合成一份路书。

这个协议让独立站、AI 模型、人工审核后台以及未来的 CRM/数据库使用同一套对象，避免出现：

- 聊天记录直接被当成客户画像或事实；
- 模型绕过城市数据库而随意推荐；
- 人工已核验的信息无法知道何时失效；
- “研究型建议”和“人工复核路书”在对外文案里混淆。

## 四个对象

| 对象 | 谁创建 | 是否可直接给客户 | 用途 |
|---|---|---|---|
| `travel_brief` | 智能体，客户确认后 | 可让客户查看/更正 | 把对话转为最小化、可修改的旅行需求摘要 |
| `retrieval_packet` | 数据库检索层 | 不直接展示 | 城市模块、意图信号、硬规则、追问和动态复核项 |
| `human_check` | 人工审核者 | 可摘要展示 | 给动态信息、资源状态与未解决风险留下日期与证据 |
| `roadbook` | 智能体初稿 + 人工发布 | 是 | 主线、备选线、客户行动项和服务边界 |

## 处理顺序

```text
用户对话
  → travel_brief（客户可更正）
  → retrieval_packet（只取匹配城市 + 规则）
  → draft_roadbook（不能叫 Human-checked）
  → human_check（日期化复核与升级/降级）
  → published_roadbook（仅通过门槛才显示 Human-checked）
  → feedback_event（回写错误、耗时、价值与字段缺口）
```

## 最关键的状态机

`research_draft` → `awaiting_human_check` → `human_checked` → `published`

可随时降级：

- 动态来源过期、天气/开放改变：`human_checked` → `awaiting_human_check`
- 客户行程或限制改变：`published` → `research_draft`
- 资源证据失效或涉及安全红线：任何状态 → `declined_or_research_only`

**只有 `published` 且存在有效 `human_check` 的路书，才允许对外出现 “Human-checked digital roadbook”。**

## 个人数据最小化

- `travel_brief` 只保存行程所需信息：日期、预算档位、兴趣、限制、语言偏好、住宿大区。
- 禁止存储护照、支付卡、精确住址、医疗病历、宗教身份等不必要信息。
- 健康/行动限制只写成“需降低台阶/步行、需人工复核”等决策字段；不做诊断。
- 客户可修改/删除其 brief；反馈引用以 `case_id` 代替姓名。

## 资源状态

`research_only`：仅作为研究方向，不在路书推荐层出现名称、价格、联系人。

`evidence_incomplete`：有候选信息但缺关键安全/商业/同意证据，不能输出。

`trial_required`：证据齐全待试运行，不能作为成熟体验销售。

`partner_ready`：已完成审核和试运行；仍只提供信息与直接联系路径，不打包代售。

`suspended`：证据过期、投诉、规则或安全变化，立即下架。

## 对接独立站的最小 API 形态（未来）

```text
POST /api/briefs                 创建/更新客户可见的 travel_brief
POST /api/retrieval              用 brief 取得模块、硬规则和追问
POST /api/roadbooks/draft        生成研究型初稿
POST /api/human-checks           审核员写入核验证据与状态
POST /api/roadbooks/:id/publish  仅在状态门槛通过时发布
POST /api/feedback               回写客户反馈与数据库修复项
```

初期不必先开发这些接口：可由表单、JSON 文件和人工 SOP 执行同样流程。网站接入时，只需遵守同一 schema。
