# 重庆首发现场运营与放行包 V1.0

适用数据库：`重庆主城智能体数据库_V1.0.json`  
适用运行包：`../chongqing-agent-runtime-v0.1/`

## 先说结论

重庆的内容、英文路书和智能体决策层已经可以服务游客；**三个在地体验仍然不可售**。放行不能靠“看过资料”或“觉得路线没问题”，只由以下两类真实证据决定：

1. 对应首发核验全部通过；
2. 对应供应商七项准入全部通过。

截至本包生成时，10 项首发核验、19 次实走、3 家候选供应商的准入均未开始。以下流程是把它们完成的最短路径。

## 首发放行地图

|---|---|---|---|

一条实走记录的 `conditional_pass`、`fail` 或 `incomplete` 都**不算通过**；一个供应商少任何一项准入也**不算已准入**。即使静态放行，实时开放、天气、许可和档期仍需在每次对客前复核。

## 出发前：先建证据目录，再开始走

为每次核验建立独立文件夹，文件名统一：

`YYYY-MM-DD_RUN001_场景简称/`

最低应包含：

- `01-track`：轨迹或分段定位；
- `02-entrance-exit`：正确入口、出口、地铁出口、下车点；
- `03-condition`：人流、台阶、坡度、施工、雨后地面；
- `04-amenities`：厕所、座椅、饮水、遮雨或降温点；
- `05-proof`：票务页、书面回复、菜单、收据、场地方规则；
- `field-record.json`：用运行包模板回填的结构化记录。

照片和视频必须保留拍摄时间；涉及常客、居民、未成年人或工作人员时，不能把其正脸当作产品素材，除非另有明确同意。

场馆、预约、交通和索道信息先查看 [动态来源复核记录](重庆动态来源复核记录_20260802.md)，再按当天官方通知核验；来源复核不能代替当天开放、施工或客流确认。

不预设具体日期，按天气和开放情况调整。可把可控场景压缩到5个现场工作日，把天气/周末触发项留为浮动任务。

1. 第一天：RUN001、RUN003，并同步完成入口卡；
2. 第二天：RUN005、RUN006、RUN009；
3. 第三天：RUN007、RUN011；
4. 第四天：RUN013、RUN015；
5. 第五天：RUN014、RUN016，并整理RUN017；
6. 触发日：RUN002、RUN004、RUN008、RUN010；
7. 实走修订后：RUN018，再做RUN019。

每完成一个任务，先回填结构化记录，再改数据库。不能先凭记忆批量更新。

## 如何回填和校验现场记录

复制 [RUN001.example.json](../chongqing-agent-runtime-v0.1/field-records/RUN001.example.json)，重命名为真实 `RUNxxx.json`，删掉所有 “Example only” 文本，填入真实信息和证据引用。

```bash
node bin/validate-field-record.mjs /absolute/path/RUN001.json
node bin/field-progress.mjs /absolute/path/to/actual-field-records
```

运行包会检查：任务ID是否合法、是否记录日期/测试人/天气人流、结论是否有足够证据，以及“通过”是否已经填写真实时长、入口出口、退出方案和变更说明。进度脚本不会把示例文件计入任何通过数；它也不会因为实走全绿就自动把体验改成可售。

## 三家供应商的七项准入

每一家都必须留下可复查的书面证据：

1. 身份、可签约主体和必要资质；
2. 英语现场口试；
3. 接待人数、服务范围、合作价及有效期；
4. 游客取消、供应商取消、天气中止的规则；
5. 商业拍摄、居民/场地隐私、内容使用边界；
6. 保险、安全责任、紧急联系人与事故流程；
7. 付款、退款和结算责任主体。

候选关系：SUP-CQ-001 对应城市解读步行，SUP-CQ-002 对应饮食体验，SUP-CQ-003 对应茶馆与黄桷坪体验。候选名单不等于推荐、合作或背书；平台资料也不等于我方尽调。

已有的中文/英文首联话术和20分钟初筛顺序，在 V1.0 工作簿的“联系工作台”和“英语口试”页。联系时不得绕开第三方平台规则，不得复制候选人的路线、照片或评价，不得写“已合作”“已入选”或承诺上架。

## 英语口试判定

10个场景总权重为100分，单项0—5分，按工作簿自动折算：

- 80分以上：英语门槛通过，仍须完成其余六项；
- 60—79分：复测；
- 60分以下：不通过。

服务者若不能说明严重过敏、湿滑台阶、隐私拍摄、取消责任或紧急情况，即使总分达到80，也应暂停进入“已准入”结论，直到该风险场景完成复测和书面证据。

## 证据到产品的更新规则

| 现场结论 | 数据库动作 | 对客动作 |
|---|---|---|
| 通过 | 在实走记录、首发核验和相关模块中写入事实、日期、证据链接 | 可保留为候选路线；动态项仍复核 |
| 有条件通过 | 写清适用天气、时段、体力或人流边界 | 只以条件路线出现，不可默认安排 |
| 不通过 | 标注失败原因并删除错误承诺 | 删除或以替代模块替换 |
| 信息不足 | 保持未开始/待执行，不用猜测补齐 | 只问询或不输出该承诺 |

体验从“仅候选”改为“可销售”前，要由人工逐项复核：所有必需 LFV 都是“通过”、供应商七项都是“通过”、英语测试通过、书面价格和取消规则有效，并且实际结算做过内部测试。之后每个订单仍要确认日期、人数、天气、开放、许可和档期。
